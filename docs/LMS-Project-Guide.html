Part A — The big picture

Start here. If you can explain this part clearly, you can survive any "tell me about your project" question.

1What the project is

LMS is an online learning platform similar to Udemy. There are two kinds of users:

RoleStored in DB asWhat they can do
Studentrole: "user"Browse the catalog, enroll (free or paid via Razorpay), watch lectures with progress tracking, ask the instructor doubts, chat with the AI tutor.
Instructorrole: "admin"Everything a student can do, plus create, edit and delete their own courses, upload lecture videos, see enrolled students, and answer doubts.
Say it like this (30 seconds)

"I built a full-stack learning platform on the MERN stack. Instructors create courses and upload lectures; students can enroll for free or pay through Razorpay, watch lectures, ask the instructor doubts and use an AI tutor powered by Google Gemini over WebSockets. Authentication uses email OTP verification, bcrypt, short-lived JWT access tokens with rotating refresh tokens, plus Google OAuth. The frontend is on Netlify, the API on Render, the database on MongoDB Atlas, and uploads go to Cloudinary."

7Client, server, HTTP and REST

Definition — client–server

The client (browser/React) sends requests; the server (Express) processes them and sends responses. They communicate over HTTP(S).

Definition — REST API

REST (Representational State Transfer) is an architectural style where resources are identified by URLs and manipulated with standard HTTP methods (GET, POST, PUT, DELETE). It is stateless: each request carries everything needed to process it.

In simple words

The URL is the thing (a course), the method is the action (read it, create it, change it, delete it). "Stateless" means the server doesn't remember you between requests. That's why every request carries your token, like showing your ID card at every door.

StatusMeaningWhere we return it
200 / 201OK / CreatedSuccessful reads; order created at checkout
400Bad requestMissing fields, wrong OTP, invalid id, failed payment signature
401UnauthenticatedNo token, expired token (code TOKEN_EXPIRED), bad refresh token
403ForbiddenA student calling an instructor-only route
404Not foundCourse or user doesn't exist
429Too many requestsThe rate limiter blocked the caller
500 / 502 / 503Server error / bad upstream / unavailableUnexpected bug / email provider failed / payments not configured
Interview tip — 401 vs 403

401 = "I don't know who you are" (log in). 403 = "I know who you are, but you're not allowed" (a student trying to create a course).

8Express: routes, middleware and error handling

Definition — middleware

A function (req, res, next) that runs between receiving a request and sending the response. It can read or modify the request, end the response, or call next() to pass control on.

// routes/admin.js — a chain of middleware, read left to right
router.post("/course/new", isAuth, isAdmin, uploadFiles, createCourse);
//                       ^ logged in? ^ instructor? ^ save file ^ do the work
In our project — the global middleware order (server/index.js)
  1. helmet() sets security headers, configured so the frontend can load our images and videos.
  2. cors() allows only our frontend origins (from CLIENT_URL).
  3. A rate limiter allows 1000 requests per 15 minutes per IP overall (stricter on auth routes).
  4. express.json({ limit: "1mb" }) parses JSON bodies.
  5. Static /uploads, then the routers, then a global error handler.
Definition — centralized error handling

An Express error handler has four arguments (err, req, res, next). Errors passed to next(err) or thrown in async handlers land there, so all errors are formatted in one place.

In our project

TryCatch(fn) wraps each controller and forwards errors to next(err). The global handler turns Multer upload errors (such as "file too large") into a 400 with a clear message, Mongoose validation and invalid-id (cast) errors into a 400, and anything else into a generic 500 message. Users never see stack traces.

9MongoDB and Mongoose

Definition — schema & model

A Mongoose schema describes the shape and rules of a document; a model is the class compiled from it that you use to query a collection (User.findById, Course.create…).

Definition — index

An index is a sorted lookup structure that makes queries on a field fast and can enforce rules like unique or auto-delete after a time (TTL).

In our project
  • razorpay_payment_id is unique, so the same payment can't be saved twice.
  • RefreshToken has a TTL index on expiresAt, so MongoDB deletes expired sessions by itself.
  • Email login uses a case-insensitive collation, so Name@Gmail.com and name@gmail.com match.
  • The connection retries every 5 seconds if Atlas is unreachable, and /health shows database: connected/disconnected.

Part C — Features in depth

The heart of your interview: authentication, tokens, email, payments, uploads and the AI tutor.

11Authentication vs authorization

Definition — authentication (AuthN)

The process of verifying who a user is, e.g. by checking a password, an OTP or a Google identity.

Definition — authorization (AuthZ)

The process of deciding what an authenticated user is allowed to do, e.g. only instructors can create courses.

In simple words

At an airport, showing your passport is authentication (proving who you are). Your boarding pass deciding whether you may enter the business lounge is authorization (what you're allowed to do).

In our project

Authentication: email + password (bcrypt), email OTP at signup, Google OAuth, and JWT access tokens on every request (isAuth). Authorization: isAdmin (instructor-only routes), plus ownership checks inside controllers (only the course's creator can edit it or add lectures; only enrolled students can open lectures or ask doubts; only the course's instructor can answer its doubts).

12Password hashing (bcrypt)

Definition — hashing

Hashing is a one-way function that turns input into a fixed-length value that can't be reversed. Passwords are stored as hashes, and a login is checked by hashing the attempt and comparing.

Definition — salt & cost factor

A salt is random data added to each password before hashing, so identical passwords get different hashes and precomputed "rainbow tables" don't work. The cost factor makes hashing deliberately slow to resist brute force.

In simple words

Hashing is like a meat grinder: you can turn a steak into mince, but not mince back into a steak. If the database leaks, attackers see only "mince". bcrypt also adds a random pinch of salt to every password and grinds slowly on purpose, so guessing millions of passwords takes forever.

In our project

bcrypt.hash(password, 10) at signup and password change (10 = cost factor, 210 rounds); bcrypt.compare() at login. The hash is never sent to the browser: publicUser() removes it and adds only a hasPassword flag.

Interview tip — hashing vs encryption

Encryption is two-way (with a key you can decrypt). Hashing is one-way. Passwords must be hashed, because even the server should never be able to recover them.

13Signup with email OTP

Definition — OTP

A One-Time Password is a short code valid for a single use and a short time, sent to something the user owns (email or phone) to prove they own it.

Signup → verify (the account is created only after the email is proven)
1BrowserPOST /api/user/register {name, email, password, role}
2ServerValidates the input, checks the email isn't taken, hashes the password, and generates a 6-digit OTP with crypto.randomInt (cryptographically secure, unlike Math.random).
3ServerPuts {user details + hashed password + OTP} inside an activation JWT signed with ACTIVATION_SECRET, valid for 15 minutes, then emails the OTP.
4BrowserKeeps the activation token in sessionStorage; the user types the code from their inbox.
5ServerPOST /api/user/verify: verifies the JWT (signature and expiry), compares the OTP, and only then creates the user in MongoDB.
Why this design is nice

Nothing is saved until the email is proven, so fake signups never fill the database. The pending signup is carried inside a signed token instead of a "pending users" table, and because it's signed, nobody can change the OTP or the role inside it.

Honest limitation (good to mention)

The JWT payload is only encoded, not encrypted. Anyone holding the activation token could decode it and read the OTP. That's acceptable because the token only lives in the same browser that's signing up. A stronger design stores only a hash of the OTP, or keeps pending signups in the database with an attempt limit.

14JWT, explained piece by piece

Definition — JWT

A JSON Web Token is a compact, URL-safe token made of three Base64URL parts, header.payload.signature. The signature (HMAC-SHA256 with a server secret, "HS256") lets the server verify the token wasn't changed and was issued by it.

eyJhbGciOiJIUzI1NiJ9 . eyJfaWQiOiI2NWYx...","cm9sZSI6InVzZXIiLCJleHAiOjE3...} . 3q2-7Hk9...
     header                       payload (claims)                                    signature
{ "alg": "HS256" }    { "_id": "65f1…", "role": "user", "iat": …, "exp": … }   HMAC(header.payload, JWT_SECRET_KEY)
In simple words

A JWT is like a concert wristband with a tamper-proof seal. Anyone can read what's printed on it (the payload is just encoded), but only the organiser can make the seal. If you change "user" to "admin", the seal breaks and the server rejects it. So never put secrets in a JWT payload.

Interview tip — "Why JWT instead of sessions?"

JWTs are stateless: the server verifies the signature without a database lookup, which scales well and works across domains (our frontend and API are on different domains). The trade-off is that a JWT can't be cancelled before it expires. That's exactly why we keep access tokens short-lived and add refresh tokens, which are stored and can be revoked (next section).

15Access token + refresh token advanced

Definition — access token

A short-lived credential (here a JWT, 15 minutes) sent with every API request to prove the user is authenticated.

Definition — refresh token

A long-lived credential (here 30 days) used only to obtain a new access token when the old one expires, without asking the user to log in again.

In simple words

Think of a hotel. The access token is your room key card. It's used all the time but expires quickly, so a lost card is useless soon. The refresh token is your booking record at reception. You show it only at reception (the /refresh endpoint) to get a fresh key card, and reception can cancel your booking at any moment (logout, password change).

Why two tokens instead of one?

One long JWT (what we had: 7 days)Access 15 min + refresh 30 days (now)
If the token is stolenThe attacker has 7 days of accessA stolen access token works for at most 15 minutes
Logout / "log out everywhere"Impossible: a JWT stays valid until it expiresThe refresh token is revoked in the DB, so the session dies
Password changedOld tokens keep workingAll other devices are signed out
User experienceLogged out suddenly after 7 daysSilent refresh: stays logged in for 30 days of use
Login → normal requests → silent refresh → logout
1LoginPOST /api/user/login returns { accessToken, refreshToken }. The server stores only the SHA-256 hash of the refresh token, plus a "family" id, in the RefreshToken collection.
2Every requestThe axios request interceptor adds token: <accessToken>. isAuth verifies it with no DB lookup for the token itself.
3After 15 minThe API answers 401 { code: "TOKEN_EXPIRED" }.
4Axios (automatic)The response interceptor calls POST /api/user/refresh { refreshToken }, saves the new pair and replays the original request. The user notices nothing.
5Server: rotationThe old refresh token is marked revokedAt / "rotated" and a brand-new one is issued in the same family. Each refresh token works once.
6LogoutPOST /api/user/logout revokes the refresh token, and the browser deletes both tokens.

The advanced parts (what makes it production-grade)

TechniqueWhat it does and why
Opaque refresh tokenA 96-character random string (crypto.randomBytes(48)), not a JWT. It means nothing by itself, so the server must look it up, which is what makes it revocable.
Hashed in the DBWe store sha256(token), like passwords. If the database leaks, the stored values can't be used to log in.
RotationEvery refresh retires the old token and issues a new one, so a refresh token is single-use.
Reuse detectionIf a retired token is used again, two parties have the same token: the real user and a thief. We can't tell which is which, so we revoke the whole family and both must log in again.
Race handlingTwo browser tabs may refresh at the same moment. The client uses the Web Locks API so only one tab refreshes, and the server allows a 20-second grace window so this isn't mistaken for theft.
Single-flight refreshIf 5 requests fail at once, the client makes one refresh call and all 5 wait for it and retry. (Tested: two parallel 401s → one /refresh → both succeed.)
Revoke on password change / resetAll sessions are revoked. The device that changed the password receives fresh tokens.
TTL cleanupMongoDB deletes expired token rows automatically.
Socket.IO tooThe socket handshake checks the access token. If it has expired, the server replies token_expired, the client refreshes and reconnects.
Interview tip — "Where do you store tokens? Isn't localStorage unsafe?"

"The ideal is an httpOnly, Secure cookie for the refresh token, so JavaScript can't read it. But our frontend (netlify.app) and API (onrender.com) are on different sites, and browsers like Safari block third-party cookies, so a cookie-based refresh would break for many users. So I store both tokens in localStorage and reduce the risk: a 15-minute access token, rotation with reuse detection, hashed storage, server-side revocation, and avoiding XSS (React escapes output, and we never use dangerouslySetInnerHTML). With a custom domain where the API is a subdomain, I'd move the refresh token to an httpOnly SameSite cookie."

16Roles and protected routes

Definition — RBAC

Role-Based Access Control grants permissions to roles (student, instructor) rather than to individual users, and checks the role before allowing an action.

// middlewares/isAuth.js (simplified)
export const isAuth = async (req, res, next) => {
  const token = req.headers.token;                         // or "Authorization: Bearer …"
  if (!token) return res.status(401).json({ message: "Please log in to continue" });
  const decoded = jwt.verify(token, process.env.JWT_SECRET_KEY); // throws if tampered/expired
  req.user = await User.findById(decoded._id).select("-password");
  next();
};
export const isAdmin = (req, res, next) =>
  req.user.role !== "admin" ? res.status(403).json({ message: "Only instructors can do this" }) : next();
Interview tip — the role is in the token; why load the user from the DB?

So that a deleted account stops working immediately, and the role always comes from the database rather than from an old token.

17Google sign-in (OAuth 2.0)

Definition — OAuth 2.0

OAuth 2.0 is an authorization framework that lets an application get limited access to a user's account on another service (Google) without ever seeing their password. We use the Authorization Code flow: Google gives our server a short-lived code, which the server exchanges, using its client secret, for the user's profile.

In simple words

Instead of creating a password with us, the user tells Google "please confirm to LMS who I am". Google sends the user back to us with a one-time ticket (the code), and our server swaps the ticket with Google for the user's name and email. We never see their Google password.

"Continue with Google"
1BrowserClicks the button → GET /auth/google on our API.
2Server (Passport)Redirects to Google's consent page with our client id, scopes (profile email) and the redirect_uri.
3GoogleThe user picks an account → Google redirects to /auth/google/callback?code=…
4ServerExchanges the code + GOOGLE_CLIENT_SECRET for the profile. Finds the user by googleId or email (linking an existing account), or creates one.
5ServerIssues our own access + refresh tokens and redirects to CLIENT_URL/auth-success#token=…&refreshToken=…
6ReactAuthSuccess reads the tokens from the #fragment, saves them, removes them from the address bar, and sends the user to their dashboard.
Why the # fragment?

Browsers never send the part after # to any server, so the tokens don't end up in Netlify's or anyone's access logs.

The OAuth errors we had in production
  • redirect_uri_mismatch: the callback URL in Google Cloud must match GOOGLE_CALLBACK_URL exactly (https, same path, no trailing slash).
  • The server crashed at startup when the Google keys were missing. Now the strategy is created per request, and a missing setup redirects to /login?err=google_not_configured.
  • "Access blocked" for other users: the consent screen was in Testing mode. Publish it.
  • Password login on a Google-only account crashed (no password to compare). Now it returns a clear message.

18Forgot and reset password

Reset flow
1BrowserPOST /api/user/forgot {email}
2ServerSigns a JWT {email} with FORGOT_SECRET_KEY (15 min), emails the link CLIENT_URL/reset-password/<token>, and stores resetPasswordExpire on the user.
3BrowserThe user opens the link, enters a new password → POST /api/user/reset
4ServerVerifies the JWT and that resetPasswordExpire is still set and in the future, hashes the new password, clears resetPasswordExpire (so the link works only once) and revokes all sessions.
Why both a JWT and a DB field?

The JWT proves the link is genuine and not expired. The DB field makes it single-use: a JWT alone could be reused until it expires.

19Email delivery

Definition — SMTP

Simple Mail Transfer Protocol: the standard protocol for sending email between servers, usually on ports 25, 465 (SSL) or 587 (STARTTLS).

Definition — HTTPS email API

Sending email by making an ordinary HTTPS request (port 443) to a provider's REST API, which then delivers the message.

In simple words

SMTP is walking into the post office through the special "mail" door. An HTTPS API is submitting the letter through the post office's website. Same result, different door. Render's free plan locks the mail door (it blocks SMTP ports to stop spam), but the web door (443) is always open.

What we tried, and why each failed

AttemptWhat happened
Gmail via nodemailer (SMTP)Worked on the laptop, but on Render the connection was silently dropped. With no timeout, signup spun forever.
Brevo (HTTPS API)The network was fine, but Brevo rejected the key ("API Key is not enabled") and the Gmail sender wasn't verified.
Resend (HTTPS API)Without a verified domain it sends only to the account owner's own address.

What we do now: a Gmail relay through Google Apps Script

Definition — Google Apps Script

A cloud JavaScript platform from Google that runs scripts inside your Google account, can use Gmail (MailApp.sendEmail), and can be deployed as a web app with a public HTTPS URL.

Sending a signup code
1Our serverPOSTs JSON {secret, to, subject, html} to the Apps Script /exec URL over HTTPS, so no SMTP is involved.
2Apps ScriptChecks that the shared secret matches (so strangers can't use it to send spam), then calls MailApp.sendEmail.
3GmailDelivers the email from your real Gmail address, so it lands in the inbox and needs no domain verification.
4Our serverReads { ok: true }. On failure it tries the next configured provider.
In our project — middlewares/sendMail.js
  • Fallback chain: Gmail script → Brevo → Resend → (SMTP only locally). The first one that succeeds wins.
  • 15-second timeout on every provider (AbortController), so a request can never hang.
  • A failure returns 502 with a friendly message. EMAIL_OTP_FALLBACK=true is an emergency switch that shows the code on screen; keep it off in production.
  • User-supplied text is HTML-escaped in templates (prevents HTML injection into emails).
  • Limit: about 100 emails a day on a free Gmail account.
Interview tip — "Why did SMTP fail in production but work locally?"

"Render's free tier blocks outbound SMTP ports to prevent abuse. Locally there's no such block. I moved email to HTTPS, which is never blocked, and added timeouts and a provider fallback so a single provider outage can't break signup."

20Payment gateway (Razorpay) advanced

Definition — payment gateway

A service that securely collects payment details (card, UPI, net banking), processes the payment with banks, and tells the merchant the result, so the merchant never handles raw card data.

In simple words

Razorpay is a trusted cashier standing between the student and the bank. Our app only says "please collect ₹1,999 for order #123". The student pays inside Razorpay's own popup. Razorpay then hands back a receipt with a tamper-proof stamp (the signature), and our server checks the stamp before unlocking the course.

Definition — order

A server-created record of the amount to collect (in paise), currency and notes. The payment must be made against this order id.

Definition — HMAC signature

A hash-based message authentication code: HMAC_SHA256(order_id + "|" + payment_id, key_secret). Only someone with the secret can produce it.

Buying a paid course
1BrowserClicks "Enroll" → POST /api/course/checkout/:id
2ServerChecks the course exists and the user isn't the owner or already enrolled. A free course is enrolled immediately. Otherwise it creates a Razorpay order: amount = price × 100 (paise), with notes {courseId, userId}, and returns {order, key_id}.
3BrowserLoads Razorpay's checkout script on demand and opens the popup with the order id and the public key id.
4RazorpayThe student pays. The handler callback receives razorpay_order_id, razorpay_payment_id, razorpay_signature.
5ServerPOST /api/verification/:id recomputes the HMAC with RAZORPAY_KEY_SECRET. If it doesn't match: 400.
6ServerFetches the order from Razorpay and checks that notes.courseId and notes.userId match this course and user.
7ServerSaves the Payment with an idempotent upsert ($setOnInsert keyed on the unique payment id) and adds the course to user.subscription once → the success page.
Security fix we made — a replay attack

The signature proves only that "this payment belongs to this order". It says nothing about which course. Before the fix, a student could pay ₹500 for a cheap course and send that valid proof to the /verification URL of a ₹2,499 course, getting it free. Step 6 closes this: the order's notes must match the course in the URL. (Tested in Razorpay test mode: the replay is rejected with 400, and the genuine payment still enrolls.)

Interview tip — key terms to use
  • Never trust the client: the amount comes from the database, not from the browser, and success is decided by the server's signature check.
  • Key id vs key secret: the id is public (sent to the browser); the secret stays on the server.
  • Idempotency: processing the same payment twice has the same effect as once (unique index + upsert + "already enrolled" check).
  • Test vs live keys: rzp_test_… keys move no real money; use test cards in development.
  • Webhooks (an improvement): Razorpay can call our server directly when a payment is captured, which covers the case where the user closes the tab before step 5.

21File uploads (Multer + Cloudinary)

Definition — multipart/form-data

The HTTP request encoding used to send files together with form fields. Multer is the Express middleware that parses it.

Instructor uploads a lecture video
1BrowserSends FormData (title, description, file) with an upload progress bar (axios onUploadProgress).
2MulterAccepts only image/video types, enforces a size limit (MAX_UPLOAD_MB, default 200) and writes a temporary file with a random UUID name.
3storage.jsIf CLOUDINARY_URL is set: uploads to Cloudinary (large videos in chunks), saves the https:// URL, and deletes the temp file. Otherwise keeps uploads/<file> on disk.
4On deleteDeleting a lecture or course also deletes its files. A file that's already gone never crashes the request.
Why Cloudinary?

Render's free server has an ephemeral disk: every deploy or restart wipes it, so uploaded videos vanished. Cloudinary stores them permanently and serves them through a fast CDN.

Definition — ephemeral filesystem

Storage that doesn't persist across restarts or deploys. Common on cloud platforms, which is why apps store files in object storage (Cloudinary, S3) instead.

22AI tutor (Gemini + Socket.IO)

Definition — WebSocket

A protocol that keeps one connection open so the client and server can both send messages at any time (full-duplex), unlike HTTP's one-request-one-response.

Definition — LLM

A Large Language Model is an AI model trained on huge amounts of text that generates text answers from a prompt. We use Google Gemini through the @google/genai SDK.

In simple words

HTTP is like sending letters: you write, wait, and get one reply. A WebSocket is a phone call: the line stays open and either side can talk. That suits a chat.

One chat message
1BrowserOpens the socket with auth: { token }. The server's io.use() verifies the JWT before accepting the connection.
2Browsersocket.emit("ai-message", text)
3ServerAdds the message to this connection's own history (capped at 20 messages and 4,000 characters), and a busy flag stops overlapping requests.
4ai.service.jsCalls Gemini with a tutor system prompt. Tries the models in order with a 25-second timeout each, falling back to the next model if one is down or retired.
5Server → Browseremit("ai-message-response", reply). React renders it as Markdown (code blocks, lists).
Bugs we fixed here
  • All users shared one chat history (it was a global variable), so one student's conversation leaked into another's. Now each connection has its own.
  • Anyone could connect without logging in (and use up our Gemini quota). Now the token is required.
  • gemini-2.5-flash was retired (404) and another model hung for 2 minutes. Fixed with a model fallback list and a timeout.

23Doubts (Q&A with instructors)

An enrolled student asks a doubt on a course (POST /api/query/create/:courseId). The course's instructor sees it in their inbox (/api/query/instructor) and replies (PUT /api/query/status/:id). The student sees the reply under "My doubts".

Authorization rules (a common interview topic)
  • Only enrolled students (or the owner) can ask on a course. Before the fix, anyone could.
  • Only the instructor of that course can reply. Before the fix, any logged-in user could answer any doubt.

28Interview questions with answers

Basics

What is the MERN stack?
MongoDB (database), Express (backend framework), React (frontend library), Node.js (JavaScript runtime). One language, JavaScript, end to end.
What is middleware in Express? Give an example from your project.
A function with (req, res, next) that runs before the route handler. For example isAuth verifies the JWT and sets req.user; isAdmin blocks non-instructors with 403; Multer parses uploads.
Difference between authentication and authorization?
Authentication verifies identity (who you are: password, OTP, Google). Authorization checks permissions (what you can do: instructor-only routes, ownership checks).
How do you store passwords?
Hashed with bcrypt (salted, cost factor 10). Never stored or returned in plain text; login uses bcrypt.compare.
What is CORS and why did you need it?
A browser security rule blocking cross-origin responses unless the server allows them. Our frontend (Netlify) and API (Render) are different origins, so the API explicitly allows our frontend URL.
What's the difference between PUT and POST?
POST creates (or performs an action, like checkout); PUT updates or replaces an existing resource, like PUT /api/course/:id to edit a course. PUT is meant to be idempotent.

Auth and tokens

What is a JWT made of? Is the payload encrypted?
Header, payload and signature, each Base64URL-encoded. The payload is only encoded, not encrypted, so anyone can read it. The signature only prevents tampering. Never put secrets in it.
Why both an access token and a refresh token?
A short access token limits damage if it's stolen and needs no DB lookup. A long refresh token, stored hashed in the DB, keeps the user logged in and can be revoked: logout, password change and theft detection all become possible.
What is refresh token rotation and reuse detection?
Each refresh returns a new refresh token and retires the old one. If a retired token is used again, it means a copy exists, so we revoke the whole token family and force a re-login.
How does the frontend refresh tokens without the user noticing?
An axios response interceptor catches a 401 TOKEN_EXPIRED, calls /refresh once (shared by all failing requests, and locked across tabs), saves the new tokens and replays the original request.
Where do you store tokens and what are the risks?
localStorage, because the frontend and API are on different sites and third-party cookies are blocked in some browsers. The XSS risk is reduced by short access tokens, rotation, reuse detection, server-side revocation and safe rendering. With a shared domain I'd use an httpOnly SameSite cookie for the refresh token.
How does Google login work in your app?
OAuth 2.0 Authorization Code flow with Passport: redirect to Google, Google returns a code to our callback, the server exchanges it (with the client secret) for the profile, finds or creates the user, issues our own tokens, and redirects to the frontend with the tokens in the URL fragment.
How does email verification work without saving unverified users?
The pending user (hashed password, role) and the OTP are placed in a signed JWT valid for 15 minutes. The account is created only when /verify receives a matching OTP and a valid token.

Payments

Walk me through the Razorpay flow.
The server creates an order (amount from the DB, in paise) → the browser opens Razorpay checkout with the order id and public key → Razorpay returns order_id, payment_id and signature → the server verifies HMAC_SHA256(order_id|payment_id, secret), checks the order's notes match the course and user, saves the payment idempotently and enrolls.
Why verify on the server? Why not trust the success callback?
Anything in the browser can be faked. Only the server knows the key secret, so only the server can confirm the signature is genuine.
What is idempotency and how did you achieve it?
Repeating an operation has the same effect as doing it once. A unique index on razorpay_payment_id, an upsert with $setOnInsert, and an "already enrolled" check mean a double submit doesn't create duplicates.
What security issue did you find in payments?
The signature check didn't tie the payment to a course, so a cheap course's payment could unlock an expensive one. I now fetch the order from Razorpay and require its notes to match the course and user.

Real-time, files and deployment

Why WebSockets for the AI chat?
A persistent two-way connection suits a chat: it's low latency, there's no repeated handshake, and the server can push the reply when Gemini finishes. Socket.IO adds reconnection and fallbacks.
How do you authenticate a socket?
The client sends the access token in the handshake (auth.token); io.use() verifies it before the connection is accepted. An expired token returns token_expired, and the client refreshes and reconnects.
Why Cloudinary instead of saving files on the server?
Render's disk is ephemeral (wiped on restart or deploy). Cloudinary gives permanent storage plus CDN delivery and video handling.
Your API was down in production. How did you debug it?
I checked /health (database disconnected), tested endpoints (DB queries failing after 10 seconds), then resolved the Atlas hostname with public DNS (NXDOMAIN, meaning the cluster was paused). After it was resumed, the data was in the lms database but the connection string defaulted to test. Adding /lms fixed it.
What happens when the free Render server is asleep?
The first request takes 30–60 seconds (cold start). The frontend uses a long timeout and shows a "waking up the server" message instead of an error.

29What I would improve next

Good answer to "What would you do with more time?"
  • Razorpay webhooks: confirm payments server-to-server even if the user closes the tab.
  • httpOnly cookie for the refresh token: put the API on a subdomain of the frontend's domain.
  • Automated tests: Jest + Supertest for the API (auth, payments), Playwright for UI flows.
  • Video streaming: HLS adaptive streaming via Cloudinary, and signed URLs so only enrolled students can fetch videos.
  • Progress on the server: lecture progress is in localStorage today; storing it in MongoDB would sync it across devices.
  • OTP hardening: store only a hash of the OTP and limit verification attempts.
  • Observability: structured logs and error tracking (e.g. Sentry), and uptime alerts on /health.
  • Paid hosting / custom domain: no cold starts, and a branded email domain for deliverability.
